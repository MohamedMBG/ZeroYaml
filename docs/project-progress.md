## Current state

Phase 1 — Foundation & Core Runtime is complete. Issue #33 and every child issue (#1-#15) are closed: the control-plane and runner foundations are bootstrapped, the shared runner gRPC contract is checked in, and the Control Plane can call `RunnerService.Ping` through a generated Java client. Runner startup configuration is externalized, so local and future deployment environments provide explicit endpoint, identity, and version settings. Runner shutdown drains in-flight RPCs within a bounded timeout and releases the listener instead of dropping work. The Control Plane hosts a `RunnerRegistrationService` gRPC server backed by an in-memory registry, and the Runner registers once at startup before serving; a Control Plane that is unreachable or that reports an identity conflict leaves the Runner status unavailable instead of silently reporting readiness. The registration service also exposes `Heartbeat`, reusing the `(runner_id, instance_id)` identity pair: a registered Runner sends a heartbeat at a configurable interval, and the Control Plane derives `HEALTHY` / `UNAVAILABLE` liveness for each registry entry from the elapsed time since its last acknowledged registration or heartbeat, with no background sweep or distributed failure detector. The core Job model and the `RunJob` gRPC contract are defined and the Runner handles `RunJob` dispatch (still rejecting every job with `JOB_REJECTION_RUNNER_UNAVAILABLE`, since execution is out of Phase 1 scope). Local infrastructure is available for development. CI/CD validates both services, requires progress updates on pull requests, protects `main` behind reviewed changes, and blocks pull requests for later phases.

The local workflow runbook for #32 is also merged, but #32 stays open pending the end-to-end test (#31). The automated test for #31 is local work and remains open. Phases 3-7 remain locked backlog.

The status-reporting path for issue #27 is merged into `main`. `JobExecutionStatusService.ReportJobStatus` carries execution facts from a Runner back to the Control Plane, which owns authoritative Job state: a running report starts a queued Job, a terminal report completes it as succeeded or failed with a reason and, where available, an exit code. Duplicate, late, and contradicting reports are answered explicitly and never change recorded state, and a terminal report repeats the execution start time so a lost running report cannot strand a finished execution. Registration and execution-status RPCs share the existing `zeroyaml.registration.port` endpoint; the proposed #26 Job log service uses a separate mTLS listener. Since #25, the Runner sends these reports for every execution it starts.

The GitHub webhook endpoint for issue #16 is merged into `main`. `POST /webhooks/github` validates the delivery envelope (event and delivery headers, JSON content type, a bounded payload that opens a JSON object), answers `push` with `202 Accepted` and hands the raw body and GitHub headers to a `GitHubWebhookDeliveryHandler`, and answers `ping` and every other event `200 OK` as ignored without starting work. Since issue #20 merged through pull request #265, the handler normalizes verified branch pushes into internal repository events behind that boundary.

Webhook signature verification for issue #17 is merged into `main`. The ingress endpoint recomputes the `X-Hub-Signature-256` HMAC-SHA256 over the raw body under a required, externally supplied secret and compares it with `MessageDigest.isEqual`, so the answer takes the same time whatever the input. A missing, malformed, or non-matching signature is answered `401 Unauthorized` and reaches neither the event allow-list nor the delivery handler, so an unverified delivery creates no internal event or job. The secret is bound from `ZEROYAML_GITHUB_WEBHOOK_SECRET`, has no default and no value in any tracked file, is never logged, and the Control Plane refuses to start without one of at least 16 characters.

The repository connection model for issue #18 is merged into `main`. It adds the `io.zeroyaml.controlplane.domain.repository` package only.

Connected repository persistence for issue #19 is merged into `main` (pull request #264). The Control Plane stores `RepositoryConnection` in PostgreSQL: a Flyway migration (`V1__create_repository_connection.sql`) creates the `repository_connection` table at startup, `JdbcRepositoryConnectionStore` implements the `RepositoryConnectionStore` port with `JdbcClient`, and `RepositoryConnectionService` connects, reads, and changes connections. A unique constraint on the canonical `(provider, owner, name)` identity rejects a duplicate connection deterministically as `DuplicateRepositoryConnectionException`, including under concurrent connects, and updates run under a `SELECT ... FOR UPDATE` row lock so concurrent changes are serialized and a failed change writes nothing. Only the webhook secret reference is stored, never secret material. The datasource is externalized through `ZEROYAML_DATABASE_URL`, `ZEROYAML_DATABASE_USERNAME`, and `ZEROYAML_DATABASE_PASSWORD` (no default), with 5-second connection and statement timeouts. No caller uses the service yet; webhook event normalization (#20) and pipeline inference (#22) are its first consumers.

The Runner Docker execution sandbox for issue #25 is merged into `main`. A Runner whose Docker daemon answers at startup and whose registration was accepted reports `accepting_work = true`, and each accepted `RunJob` starts a background execution: a workspace volume, a checkout container that fetches the dispatched revision, and a Job container that runs the dispatched command as its entrypoint in the dispatched working directory, under memory, process-count, and `no-new-privileges` bounds and a configurable timeout. Every container and the volume are removed on success, failure, timeout, and cancellation, and each execution sends a running and a terminal status report through the issue #27 reporter. Job image and timeout are Runner configuration because the `runner.v1` contract does not carry them yet.

## Risks and blockers

- Enabling the #26 reader requires native HTTP-server TLS and explicit `server.forward-headers-strategy=NONE`. Existing reader deployments must provision the HTTP certificate/key and update clients to HTTPS; proxies must re-encrypt to the Control Plane. Enabling TLS changes the primary HTTP listener for webhook and actuator callers too. Reader rejection cannot protect a token a client has already sent in plaintext, so clients must use HTTPS from the first request.
- The #26 log ingress needs externally provisioned mTLS certificates and remains disabled until configured. Retention is process-local and best effort. At capacity, streams with a final marker or five minutes of local receipt inactivity can be evicted, oldest admitted first. A running Job silent for that interval may lose earlier output; later records can start a new retained fragment. If all slots contain recent active output, new logs return `RESOURCE_EXHAUSTED`. Output still undelivered when the 35-second post-exit drain bound expires is dropped and the log is marked incomplete. The pending flush and final marker then have five more seconds, of which the pending chunks may use only half, so log delivery can delay the terminal status report by at most 40 seconds after command exit, excluding container cleanup; a final marker that misses that bound is lost, leaving completeness unknown. A Job whose container never started has no log record, so the reader answers `404` and the terminal status report carries the failure. Daemon-side log rotation behind a follower held back by delivery is not detected or flagged; two 10 MB log files reduce that risk and use at most 20 MB of daemon disk per running Job. Restart loses logs. The read endpoint is protected by one shared bearer token, so anyone holding it can read every retained log until user authentication exists. No automatic secret redaction, durable log storage, or UI is included. Registration/status authentication is unchanged.
- Log output is attributed to the Runner assignment recorded by dispatch before `RunJob`. `ReportJobStatus` remains unauthenticated: a sender that learns a dispatched Job's `runner_id` and `instance_id`, for example by observing the plaintext status port, can still report status for that Job. Authenticating the status RPC belongs to Phase 6 transport security (issues #231-#242).
- stdout and stderr are ordered relative to each other only at chunk granularity (up to 4 KiB per stream). For example, a `set -x` trace on stderr can arrive after the stdout output it introduced. This is the trade-off against the chunk budget; line-level ordering would need several stream segments per record, which is a `runner.v1` contract change. It partly meets the "preserve useful ordering between output streams where feasible" scope item of #26.
- `RunnerFacingGrpcServer` still uses grpc-java's default unbounded executor; the log listener is bounded. Bounding the registration/status listener is tracked by #280.
- Lifecycle events can be lost if a broker outage lasts longer than the 30 s delivery bound, if more than `queue-capacity` events are waiting, or if the Control Plane stops between commit and send. There is no transactional outbox. A consumer that needs guaranteed delivery needs a follow-up issue. Events for one Job can be queued out of order when two reports for it are reconciled concurrently. Consumers order them by lifecycle stage, as documented.
- Queueing and cancellation have no lifecycle event types. The #30 orchestration queues and cancels Jobs but publishes neither `job.queued` nor `job.cancelled`, so a consumer cannot tell a cancelled step from one that is still waiting. Adding those types needs its own issue.
- With #19 applied, the Control Plane needs a reachable PostgreSQL database at startup, because Flyway migrates before the service accepts traffic. Control Plane tests start a `postgres:16-alpine` container through Testcontainers, so `mvnw test` and `mvnw verify` need a running Docker daemon.
- The #19 unique constraint covers `DISCONNECTED` connections, so a disconnected repository cannot be connected again yet. Reactivating or archiving the old row needs its own issue together with a reconnect flow.
- Neither side retries a status report. A report lost in transit is recovered by the reconciliation rules rather than by resending; bounded retry with backoff remains Phase 5 work.
- `secret-scan` and `static-analysis` are new check names. They gate merges only after the branch protection rule for `main` lists them, which follows their first successful run.
- `.coderabbit.yaml` takes effect only once the CodeRabbit GitHub App is installed on the repository.
- The Semgrep run excludes `go.grpc.security.grpc-server-insecure-connection` while the Runner gRPC server is deliberately plaintext. That exclusion is removed with Phase 6 transport security (issues #231-#242).
- The execution sandbox targets local development. Containers use Docker's default bridge network and a root-owned workspace, and a remote repository location with embedded credentials is visible through `docker inspect` while the checkout container exists. Multi-tenant isolation hardening stays out of Phase 2 scope.
- Tests that start real containers are opt-in (`ZEROYAML_RUNNER_DOCKER_TESTS=1`) because they need a Docker daemon and pinned public images, so CI covers the sandbox through a scripted Docker CLI only.
- Runner shutdown is bounded by `ZEROYAML_RUNNER_SHUTDOWN_TIMEOUT` (default `5s`), which covers the RPC drain and the execution drain together. A slow Docker cleanup can therefore outlive the process and leave labelled containers or volumes behind; they are logged and removable by label until execution state survives a restart (#28).
- The Control Plane refuses to start without `ZEROYAML_GITHUB_WEBHOOK_SECRET`. Every environment and any future deployment pipeline must supply one before the service is started.
- One webhook secret is configured for the whole Control Plane. Per-repository secrets and rotation without downtime are not supported. Repository metadata persistence (#19) stores only the name of a secret per connection and nothing resolves it during verification; per-repository resolution and rotation need their own issue alongside Phase 6 security work.
- A verified delivery can still be replayed: identical redeliveries normalize to equal events, but ingress does not suppress or persist delivery IDs. Durable duplicate handling is tracked as issue #203.
- `docs/local-development-workflow.md` documents two separately verified halves rather than one continuous push-to-execution run. Its expected-state and automated-coverage sections must be re-verified against the end-to-end test from #31; acceptance criteria of #32 that depend on that test remain unmet until then.
- The documented local workflow was executed by hand once, on Windows on 2026-10-11: startup, the signed delivery with its negative checks, and one succeeded and one failed Job execution. The bash blocks ran under Git Bash on Windows only and were not run on Linux or macOS; the runbook states this next to its shell guidance. The delivery from GitHub itself (Section 7.2) and the persistence restart check were not executed and are marked as such in the runbook. The two halves were not run as one continuous scenario. No automated check asserts that the runbook's commands, log lines, or response codes still match the code, so a behavior change can leave it stale until the next manual run.
- A Runner restarted after an accepted registration is rejected with an identity conflict until the Control Plane restarts, because each Runner process generates a new instance identifier and the in-memory registry never releases the earlier one. The runbook documents the workaround; releasing or replacing a stale registration is tracked as issue #271.
- The #24 selector checks liveness and startup Docker capability only; current readiness, capacity, and network reachability are not reported by the existing heartbeat. Dispatch still reaches one configured endpoint (`zeroyaml.runner.host`, `zeroyaml.runner.port`). The #30 implementation enforces the selection against that endpoint: an acknowledgment from any Runner process other than the selected one cancels the Job. Routing to several Runners needs its own issue.
- Job creation for #23 is idempotent across Control Plane restarts because the #28 store makes recorded Jobs durable. A changed plan for a revision still records new Jobs beside the earlier plan; deciding whether to stop or supersede them belongs to Phase 3. The webhook path calls Job creation, so a redelivered push records no new Jobs.
- #30 orchestration is not durable. Pushes and step completions wait in a process-local queue of 64 entries, so a Control Plane restart loses waiting work. A redelivered push dispatches a step that waited for a Runner and advances a pipeline whose completion was lost. A Job whose `RunJob` outcome is unknown stays queued and assigned even then; recovering it is Phase 5 work (#210).
- Every pipeline step runs with the Runner's configured Job image and timeout, because `runner.v1` does not carry them. The default `alpine:3.22` image has no JDK, so the Maven scenario needs `ZEROYAML_RUNNER_JOB_IMAGE` set to an image that provides one.
- The Runner's single startup registration attempt can exceed its `5s` default bound when resolving `localhost` is slow, which was observed on Windows and leaves the Runner unavailable. The runbook documents the `127.0.0.1` workaround; no retry exists for the startup registration yet, and bounded retry is tracked as issue #272.
